q.e.d. has two new settings dialogs. **Site settings** edits `site.toml`:
title, description, language, web address, and the website's theme.
**App settings** (the ⚙ in the header) picks a theme for the q.e.d. app itself.
The two are independent: write in a calm dark app, publish a bright website.

## How a daisyUI theme works

[daisyUI](https://daisyui.com/docs/themes/) defines each theme as a set of
CSS variables (`--color-primary`, `--color-base-100`, …) under a selector
like `[data-theme=cupcake]`. Every component and utility class (`bg-primary`,
`btn`, `card`) uses those variables, never fixed colors. So switching the
whole look is one attribute:

```html
<html data-theme="cupcake">
```

The attribute can sit on any element, and everything inside follows it. The
theme picker uses that: each swatch is a button with its own `data-theme`,
so it's drawn in the theme it stands for.

```svelte
<button data-theme={theme} class="bg-base-100 …">
  <span class="bg-primary"></span>
  <span class="bg-secondary"></span>
  …
</button>
```

Without any `data-theme`, daisyUI uses light, and switches to dark when the
system is in dark mode. That's what "Follow system" means in the app: the
attribute is simply removed.

## Where each choice lives

The **website's** theme is part of the site, so it's in `site.toml` and
travels with the folder. Saving uses the same format-keeping writer as page
files (see the [post on saving](2026-10-21-saving-without-breaking.md)), so
comments in `site.toml` survive.

The **app's** theme is a preference of whoever uses the app on this
computer. It doesn't belong to any site, so it's kept in the app window's
own browser storage, in [`appTheme.ts`](../../../src/lib/appTheme.ts):

```ts
export function loadAppTheme(): string | null {
  try {
    return localStorage.getItem(KEY);
  } catch {
    return null;
  }
}
```

The `try` is there because storage can be unavailable; then the choice
simply lasts until the app closes. Elixir's equivalent would be wrapping a
call that may raise in `try … rescue`, which is rarer there; in JavaScript,
storage access is a well-known place for exceptions.

## One list of themes

The site stylesheet is compiled with all 35 daisyUI themes, and `site.toml`
may only name one of those. The list lives once, in Rust, in
[`theme.rs`](../../../crates/qed-core/src/theme.rs), with a test that checks
it against the compiled stylesheet:

```rust
#[test]
fn matches_the_themes_in_the_site_stylesheet() {
    let css = include_str!("../assets/site.css");
    for theme in THEMES {
        assert!(css.contains(&format!("[data-theme={theme}]")), "{theme} is missing from site.css");
    }
}
```

The UI doesn't keep its own copy; it asks Rust with a tiny command,
`list_themes`. After the [`kind` mix-up](2026-10-21-publishing-over-sftp.md)
between hand-written TypeScript and Rust types, having one source for such
lists is worth the extra call.
