# qed: guidelines for coding agents

qed is a single-user desktop app: Rust + Tauri 2, with a SvelteKit (Svelte 5,
TypeScript) single-page UI styled with Tailwind v4 + daisyUI 5. Open work and
decisions live in `docs/pages/backlog.md` (items `#nnn`; finished ones move
to `docs/pages/done.md`); read the backlog first and keep both current.

## Layout

- `crates/qed-core`: all domain logic (site folder format, pages and blocks,
  site generator, publishers). No Tauri or UI dependencies; test it with
  `cargo test -p qed-core`.
- `src-tauri`: thin shell. Tauri commands only convert arguments and call
  qed-core.
- `src`: the UI. It talks to Rust only through `commands` from
  `src/lib/site.ts`. `src/lib/bindings.ts` is generated by tauri-specta from
  `commands()` in `src-tauri`; don't edit it. `cargo test` rewrites it when a
  command or a type changed (and fails once), so run the tests twice after
  such a change and commit the file. New commands need `#[specta::specta]`
  and an entry in `commands()`; new types crossing to the UI need
  `#[cfg_attr(feature = "specta", derive(specta::Type))]`.
- `crates/qed-core/templates`: askama templates for generated sites. After
  changing CSS classes there, run `npm run build:site-css` and commit
  `crates/qed-core/assets/site.css`.
- Build a site without the app: `cargo run -p qed-core --example build -- docs`.
  Output goes to `<site>/_site/` (git-ignored).

## Data

There is no database. A site is a folder: `site.toml`, Markdown pages and
posts (plus `footer.md` for the site footer's blocks and `shared/*.md`
for shared blocks shown on several pages) with TOML front matter (`+++`), block containers (`::: type` … `:::`;
Columns use `:::: columns` with `::: column` lines inside) inside the
Markdown, `media/` (images), `assets/` (files to download) and `static/` (copied into
the built site as it is) and `fonts/` (self-hosted fonts from Fontsource). History is git.
Secrets (SSH keys, tokens) live in the OS keychain, never in the site folder.

## Rules

- Run `npm run check:all` before finishing: rustfmt, clippy with
  `-D warnings`, Rust tests and svelte-check must pass.
- Return `Result` with a typed error from qed-core; no `unwrap`/`expect`
  outside tests and `main`/`run`.
- Svelte 5 runes only (`$state`, `$derived`, `$effect`, `$props`); no legacy
  `export let` or stores for component state.
- Give key UI elements stable `id`s.
- Front-end code from others that generated sites use (the Podlove
  Subscribe Button, later the Podlove Web Player) is copied into
  `crates/qed-core/assets/<name>/` with a `README.md` that says where the
  copy comes from (project, version or commit, date), what was changed,
  how q.e.d. uses it and how to update it.
- Don't write inline `<script>` tags into generated sites without need.
  Content must be readable without JavaScript; JavaScript is only for
  optional features that degrade gracefully, such as the player and site
  search (#108).

## Manual

The user manual (#110) is for site owners and editors, not developers:
`docs/pages/manual/`, on the docs site under `/manual` and compiled into
the app (`qed_core::manual`, opened with the Manual button). Manual
pages link to each other by file name (`versions.md`) and to anything
else with a full web address, so the links work in both places;
`cargo test` fails on one that doesn't. Use blocks (columns, FAQ, call
to action, text with image) and icons next to button names
(`:icon-eye:`), and name buttons exactly as the app does. Screenshots go
into `docs/media/manual/` and are always taken with the app's own theme
set to *catppuccin-mocha* (App tab), so they look the same throughout.
When a change alters what a manual page describes, update the page, and
its German translation beside it (`versions.de.md`, #145): German with
"Sie", button and tab names in English exactly as the app shows them.
The docs site has German only for the manual and the start page
(`index.de.md`); the rest (blog, changelog, backlog) stays English.
`libraries.md` is written by `cargo run -p qed-core --example libraries`;
run it after adding or updating dependencies (a test fails until then).

## Learning blog

The owner is learning Rust, Svelte and TypeScript through this project. When a
change introduces a concept new to the project, explain it in a post in
`docs/pages/blog/` (`YYYY-MM-DD-slug.md`, TOML front matter), tied to the concrete
code, comparing with Elixir where it helps, with links to the official docs.
Give each post a short `title` that fits the docs site's sidebar (about 25
characters), the full headline as `description`, `menu = "main"`, the next
`weight` (posts are numbered in the order written), `date`, `authors`,
`tags` and `summary`. Name source files as code (`` `src/lib/site.ts` ``),
don't link them: links may not leave the site folder, and the build stops
on one that does. The blog's front page lists posts by itself (a Post
list block). `docs/` is a qed site; `cargo test` fails if
it stops being valid. Don't explain in chat what belongs in a post.
